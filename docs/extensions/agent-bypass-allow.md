# Bypass auto-allow (Claude Code & Antigravity CLI)

[Documentation](../README.md) · [Source](../../extensions/agent-bypass-allow/)

Claude Code in `bypassPermissions` mode (`--dangerously-skip-permissions`, "bypass permissions on") and Google Antigravity CLI (`agy`, driven through `agy acp` with `toolPermission: "always-proceed"`) still stop on some calls and wait for someone to choose **Yes**. Persona then shows the agent as waiting for you, and an unattended run, often a subagent, stalls until someone answers or the CLI times out. On the computers you choose, this extension adds a Claude Code `PermissionRequest` hook and an Antigravity `PreToolUse` hook. It allows those prompts only in bypass sessions (`bypassPermissions` / `always-proceed`), only for Bash (`run_command`), the read-only tools and subagents, and never for a command that deletes or overwrites data outside temporary and work directories, forces a push or changes permissions. A `Read` or `read_file` rule of yours covers `Glob`, `Grep`, `LS` and `NotebookRead` too. In every other case, it stays silent and the agent asks as usual.

## What still prompts in bypass mode

Measured with Claude Code 2.1.308 in a throwaway project:

| Command | Prompts in bypass mode |
| --- | --- |
| `cd view && rm -f sub/*` (a relative glob after `cd`) | Yes: "Dangerous rm operation on statically-unresolvable target" |
| `for d in …; do rm -rf "$t"; done` (a target built at run time) | Yes, same check |
| A Bash command matching your own `permissions.ask` rule, such as `Bash(touch:*)` | Yes: "Permission rule … requires confirmation" |
| A 12,000-character one-liner, a heredoc, `eval`, a `for` loop, `X=view; rm -rf "$X"/x` | No |
| Read, Glob or Grep of a path outside the working directories, when reads outside them are blocked | Yes: "Read outside the working directories" |

Length alone does not trigger a prompt. Claude Code has a small set of safety checks that bypass mode does not skip. Its build calls them *bypass-immune*. For Bash, the main one is *dangerous removal*: an `rm` or `rmdir` whose target cannot be resolved before the command runs. Examples are a glob after `cd`, a variable or `$(...)` target, and an `rm` inside a `bash -c` script that Claude Code cannot parse. Claude Code runs `PermissionRequest` hooks for these prompts. The hook input includes `permission_mode`, and a hook's `allow` is honoured. When several hooks are configured, the first `allow` wins, so this hook does not wait for slower ones. Persona's own hook, which sends the prompt to your phone, is one of them.

## Shell-parser confirmations (0.2.32)

A parser warning is not proof of a deletion. The reported Claude Code 2.1.312 message, `Dangerous rm operation not ruled out - the shell may read this command differently than it was parsed`, can accompany a harmless zsh probe such as `k=PATH; v="${(P)k}"; printf '%s\\n' "$v"`. The hook judges the original command, not the warning text, so an eligible probe is allowed even though Claude Code could not parse it. The quoted probe was already allowed by the existing policy; 0.2.32 adds explicit regression coverage rather than claiming a new hook mechanism.

Version 0.2.32 also keeps simple zsh parameter flags together when scanning unquoted words. For destructive targets, it resolves the exact `${(P)name}` form only when both the selector and the selected variable are known from the same command under the existing assignment/taint rules. For example, `k=S; S=/tmp/cache; rm -rf "${(P)k}"` goes through when the resolved target is scratch. Unknown, computed, conditionally assigned or tainted selectors/values are not resolved; with the destructive override off they still ask. For indirect targets, the presence of variable-setting builtins, sourced scripts or arithmetic also disables this new resolution path, because their dynamic target names cannot be tracked safely. Other zsh flags are not evaluated by the hook.

The following categories use the same policy; no error-message allowlist is needed:

| Confirmation category | Extension behavior |
| --- | --- |
| Unsupported shell syntax in a harmless Bash command, including quoted `${(P)k}`, read-only process substitutions and ordinary shell scripts | Allows when the hook receives an eligible bypass-mode request and no guard or user rule applies |
| Statically unresolved removal, such as a relative glob after `cd` or a variable target | Allows only when every target resolves into scratch; the explicit destructive override can allow other deletions subject to the protected-target floor |
| Read restrictions or additional machine checks on the supported read-only tools and subagents | Uses the same bypass/matcher/heartbeat/user-rule gates; the warning label does not change the decision |
| Dynamic executable, such as `"${(P)k}" -rf /` or `env "$cmd" -rf /`; evaluated zsh `${(e)name}` expansion | Leaves confirmation in place, including with the destructive override on |
| Explicit ask/deny rule, unsupported tool, non-bypass mode, missing/stale heartbeat | Leaves the request alone |
| Human-only confirmation, a request never sent to this hook, or an independently enforced sandbox/organization restriction | Cannot approve it; does not work around the host restriction |

Known deletion targets resolving to `/`, the hook computer's entire home directory or an ancestor of that home, including wildcard prefixes and followed symlink paths, always ask even with `allow_destructive` on. Removing a symlink itself is not removing the directory it points to: `rm -f /tmp/home-link` can still be scratch, while `rm -rf /tmp/home-link/` does not bypass this floor. This is a conservative command inspection, not a complete shell interpreter or a filesystem enforcement layer. Unknown targets under the explicit destructive override, remote home directories, aliases, sourced scripts, commands built by another program and changes after inspection cannot all be proved safe. Keep that override off for unattended work if those boundaries matter.

## Other agents and requests this extension cannot answer

Claude Code's [permission-mode exceptions](https://code.claude.com/docs/en/permission-modes#actions-no-mode-auto-approves) distinguish approval from denial and user interaction: explicit ask rules, critical-path removals, configured outside-directory read blocks, interactive tools and some cross-machine communication can still stop a bypass session. A protected `.claude` write is not generally a bypass exception; `auto` classifier timeouts are not evidence about bypass mode. Force pushes, permission changes and SQL deletion are this extension's own conservative floor, not a claim that Claude Code always asks about them in bypass.

The [PermissionRequest contract](https://code.claude.com/docs/en/hooks#permissionrequest) covers actual tool approval requests, including eligible bypass/headless requests. It does not cover sandbox network approvals, and its `allow` cannot undo an earlier deny or a later OS/worktree isolation failure. [Critical-path removal rules](https://code.claude.com/docs/en/permission-modes#the-dangerous-rm-operation-not-ruled-out-prompt) also explain why a `PreToolUse` allow or an ordinary Bash allow rule is not a substitute for this extension's `PermissionRequest` response. No launcher flags or bypass-waiver environment variables are changed here.

| Agent or request path | Coverage and remaining limit |
| --- | --- |
| Claude Code 2.1.329 (investigated locally), with historical reports from 2.1.312 | The installed `PermissionRequest` matcher handles Bash, supported readers and Agent/Task in bypass; human-interaction tools, MCP/connector approvals, Workflow, network approvals and hard restrictions remain outside it |
| Antigravity CLI 1.5.13 (installed locally) | The existing `PreToolUse` / `always-proceed` adapter shares the guard and the new regression tests; no complete public inventory of its forced-confirmation policy was established |
| Codex CLI 0.159.3 | Not installed or registered by this extension. This Codex version has permission-request hooks, but a dangerous command under `approval_policy=Never` can become `Forbidden` before those hooks run; that is a denial, not a prompt this extension could automatically approve |
| Gemini CLI | Not adapted by this extension. Its policy engine selects allow/deny/ask by mode and priority, and noninteractive ask can become deny; YOLO is not evidence that explicit policies or hard restrictions disappear |

Versioned Codex sources: [bypass CLI mapping](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/cli/src/main.rs#L1988), [dangerous-command handling under Never](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/core/src/exec_policy.rs#L793), [early Forbidden return](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/core/src/tools/orchestrator.rs#L196), [approval hooks](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/core/src/tools/approvals.rs#L505). Gemini sources: [policy engine](https://github.com/google-gemini/gemini-cli/blob/d4cb1713fd7fc30f1c03f9ca7cbfed341c97dffd/docs/reference/policy-engine.md) and [hooks](https://github.com/google-gemini/gemini-cli/blob/d4cb1713fd7fc30f1c03f9ca7cbfed341c97dffd/docs/hooks/reference.md). zsh documents the [P and e parameter-expansion flags](https://zsh.sourceforge.io/Doc/Release/Expansion.html#Parameter-Expansion-Flags).

This inventory is versioned, not a promise to approve every current or future agent request. Starting a new supported session with the hook installed is necessary; upgrading only the package does not fix a session that loaded settings before installation. [Persona assistant channel profiles](#persona-assistant-channel-profiles) describes the automatic discovery and reconciliation added in 0.2.37.

## What it allows, and what it leaves alone

The hook answers `allow` only if all of these hold:

- The session's permission mode is `bypassPermissions` (for `agy`, `toolPermission: "always-proceed"` with no non-bypass `agentMode`, or an explicit `bypassPermissions` mode), and the tool is `Bash` (`run_command`), a read-only tool (`Read`/`read_file`/`view_file`, `Glob`/`find_by_name`, `Grep`/`grep_search`, `LS`/`list_dir`, `NotebookRead`) or `Agent` (`Task` in older Claude Code versions, `invoke_subagent` in `agy`). A subagent's own calls come to the hook one by one and are judged the same way. Other modes (`default`, `acceptEdits`/`accept-edits`, `plan`, `auto`, `request-review`) and other tools, including MCP tools, `Write`/`write_file`, `Edit`/`edit_file`, `MultiEdit`, `NotebookEdit` and `Workflow`/`run_workflow`, are never answered (the one exception is the `assistant_writes` setting, in [Persona assistant writes](#persona-assistant-writes)). The settings entry's matcher lists only these tools.
- For Bash, the command is not one that stays with a person. These are: deletion (`rm`, `rmdir`, `unlink`, `shred`, `rimraf`, `find -delete` (and whatever `find -exec` runs), `git clean`, `git rm`, `git branch -d`/`-D`/`-M`/`--delete-merged`, `git tag -d`/`-f`, `git stash drop`/`clear`, `git worktree remove`, `git filter-branch`/`filter-repo`, `git reflog expire`, `git update-ref -d`/`--stdin`, `rsync --delete`/`--del*`, `docker rm`/`prune`, `docker compose down -v`, `kubectl delete`, `terraform destroy`, `aws … delete-*`/`s3 rm`/`s3 rb`/`--delete`, `gcloud … delete`, `az … delete`, `gh … delete`, `gh repo archive`, `gh pr merge --delete-branch`, `gh api -X DELETE`, SQL `DROP`/`TRUNCATE`/`DELETE FROM`); overwriting data (`>`, `>|`, `N>` or `&>` into a file outside `/dev/` and the scratch directories, `tee` without `-a` into such a file, `sed -i`/`perl -i`, `find -fprint`/`-fprint0`/`-fprintf`/`-fls`, `ln -f`, `mv`, `cp -f`, `dd`, `mkfs*`, `truncate`, `git reset --hard`, `git checkout -f`/`--`/`.`, `git checkout <commit> <path>`, `git checkout -B`, `git switch -C`/`--orphan`, `git restore`, `git switch --discard-changes`); a forced or deleting push (`--force*`, `-f`, `-d`, `--mirror`, `--delete`, `--prune`, `+ref`, `:ref`); and permission changes (`chmod`, `chown`, `chgrp`, `install -m`/`-o`/`-g`, `chattr`, `setfacl`, `usermod`, `passwd`, `visudo`, `setcap`, SQL `GRANT`/`REVOKE`/`ALTER USER`, `gh secret`/`variable`/`ssh-key`/`gpg-key`, `gh repo edit --visibility`, `gh repo deploy-key`, a `gh api` write to collaborators, permissions, branch protection, teams, members, keys, secrets, hooks or environments or that sets `visibility`/`private`, a `gh api graphql` mutation, `aws iam` and `put-*-policy`/`put-*-acl`, `gcloud … iam-policy`, `az role`, creating or changing Kubernetes roles and bindings). The `gh` checks read the command after gh's `-R`/`--repo` flag too (`gh -R owner/repo secret set X`). A shortened git long option counts like the full one, as git reads it (`git reset --har`, `git push --dele`). The git subcommand is read after global options that take a value (`-C`, `-c`, `--namespace`, `--config-env` and the like), and a `git -c alias.*` without `!` is read as the git command it expands to (`git -c alias.x=clean x`); an alias set with `--config-env` stays with you. The command is split the way a shell splits it. Its `$'…'` and `$"…"` quotes are decoded (`$'\x72m'` is `rm`), braces are expanded (`{rm,-rf,x}`, `r{m,}`), a comment is skipped, and a program word with a glob in it (`/bin/r?`) counts as each program it can match. A program name counts whatever its letter case, since macOS file systems ignore case by default and `RM`, `/bin/Rm` or `ſudo` (with a long s) runs `rm` or `sudo`. A word counts as a program when it comes first or after a wrapper (`sudo`, `xargs`, `env`, `timeout`, `find -exec`, `unshare`, `taskset`, `caffeinate`, `arch`, `xcrun`, `nsenter`, `toybox`, `torsocks`, `proxychains`, `firejail`, `bwrap`, `uv run`, `bundle exec`, `coproc`, `do`, `then` and the like), so `grep -rn truncate src/` and `git mv a b` go through and `sudo -b rm x` does not. Every part of a list, pipeline or substitution counts. A quoted argument is read again as a command when a shell or command runner runs it (`bash -c`, `sh -c`, `csh -c`, `tcsh -c`, `pwsh -c`, `ssh host '…'`, `eval`, `env -S`, `flock -c`, `script -c`, `sg -c`, `npx -c`, `trap`, `git rebase -x`, `git submodule foreach`) or when it holds a substitution (`$(…)`, backticks), and commands run by `git bisect run` or a `git -c` value that is a command (`alias.*='!…'`, `core.sshCommand`, `core.editor`, `diff.external` and the like) count, and so does a variable git runs the same way when it is set on the command (`GIT_SSH_COMMAND`, `GIT_EDITOR`, `GIT_SEQUENCE_EDITOR`, `GIT_EXTERNAL_DIFF`, `GIT_PAGER`, `PAGER`, `EDITOR`, `VISUAL`, before the program, after `env`, or by `export`/`declare`/`typeset`/`readonly`/`local`), so `bash -c 'rm -rf x'` and `git commit -m "$(rm -rf x)"` stay with you. Output written with `>`, `>|`, `N>` or `&>` overwrites a file and stays with you, except into `/dev/…` or `/tmp/…` that lands under `/dev` or a temporary directory once `..` and symlinks are resolved as the kernel reads them (`/tmp/../etc/hosts` and `/tmp/link/x` with the link leading to your home directory stay with you, while `/tmp/a/../b` goes through on macOS, where `/tmp` leads to `/private/tmp`); in a command that makes links or mounts only `/dev/…` goes through; `>>` appends and goes through. SQL counts only in a command that runs a SQL client (`psql`, `mysql`, `sqlite3` and similar), including a heredoc fed to it. Free text is not read: `git -m`/`--message`, and `gh --title`/`--body`/`--notes`, so `git commit -m 'drop rm wrapper'` goes through; neither is the body of a heredoc fed to anything but a shell (`sudo -s`, `sudo -i` and `doas -s` start one) or a SQL client, such as `cat > /tmp/x <<EOF`. Only a `<<` the shell reads as a heredoc starts one: after a `<<` inside quotes (`echo 'usage: x <<FILE'`), backticks, a comment or arithmetic (`$((1<<n))`), the lines are still read as commands, and a body starts only after the line the command ends on. A command hidden in a variable, a script file or another program's input is not seen, nor is a deletion done inside a script language (`python3 -c 'shutil.rmtree(…)'`, `perl -e 'unlink …'`).
- A deletion or overwrite whose targets are all in temporary or work directories goes through anyway (next section). With the `allow_destructive` setting on, other deletions and overwrites go through, but known root/home deletion targets, dynamically selected executables and evaluated zsh expansions remain with a person. A forced push, a permission change, disk formatting (`mkfs*`, `wipefs`, `fdisk`, `parted`, `dd of=/dev/…`), a `gh api graphql` mutation and a command the hook cannot read still ask.
- The extension's program is running on that computer. It refreshes a heartbeat every minute. If the heartbeat is more than five minutes old, the hook allows nothing. This covers the case where the program was killed before it could remove its entry.
- None of your own `ask` or `deny` rules could apply to the call. For tools other than Bash, any rule naming the tool counts for every call of it, whatever its pattern: `Read(./secrets/**)` or `read_file(.env)` keeps every Read prompt with you, `write_file(...)` covers both `Write` and `Edit`, and a rule for `Task` or `invoke_subagent` counts for `Agent`. For Bash rules: The hook reads Claude Code's managed settings, `<config dir>/settings.json`, `<config dir>/settings.example.json`, and `.claude/settings.json` / `.claude/settings.example.json` in the working directory and each parent; for `agy`, it also reads Antigravity's managed `admin_settings.json`, `<agy dir>/settings.json`, `<gemini dir>/config/config.json` (`globalPermissionGrants`), and `.agents/settings.json`, `.agent/settings.json` and `.gemini/settings.json` across the working and workspace directories and their parents (`command(...)` and `run_command(...)` match like `Bash(...)`). A rule counts when the literal start of its pattern appears anywhere in the command, either as written or after quotes, backslashes and line continuations are removed and each run of whitespace becomes one space. For example, `Bash(git push:*)` or `command(git push*)` counts for `cd x && git push`, `git  push` and `'git' push`, and a bare `Bash` or `command(*)` counts for everything. Flags in another order are not matched: `Bash(rm -rf:*)` does not count for `rm -fr` or `rm -r -f`, and Claude Code 2.1.318 does not ask for those either. This errs toward asking. Claude Code applies `deny` rules before it asks, so those calls never reach the hook; they are checked anyway.

The hook cannot see rules passed on the command line (`--settings`, `--allowedTools`/`--disallowedTools`), rules added in the session with `/permissions` and not saved, or project settings outside the session's working directory and its parents. If an `ask` rule exists only in one of those places, Claude Code's prompt for it will be auto-allowed in bypass mode. Put rules you depend on into a settings file.

The hook also answers other safety checks, such as Claude Code's isolated-peer-machine and read-block checks, when they are raised by one of the tools above. Prompts that Claude Code marks as approvable only by a person, such as edits to its own settings files or a classifier timeout in `auto` mode, ignore a hook's `allow`; this extension does not try to work around them. The `Run a dynamic workflow?` prompt is for the `Workflow` tool, which the hook never answers.

Before 0.2.0, the hook answered every Bash prompt in bypass mode, including dangerous removals, and nothing else.

This floor only decides which of Claude Code's own prompts the hook leaves to you. In `bypassPermissions` mode Claude Code runs most commands without asking at all, including a `git push --force` or an `rm` whose target it can resolve; the hook never sees those calls and cannot stop them.

## Deletions in temporary and work directories

An `rm`, `rmdir`, `unlink`, `shred`, `rimraf`, `trash`, `truncate`, `mv`, `cp -f`, `ln -f`, `tee`, `find -delete`, `find -fprint` (and `-fprint0`, `-fprintf`, `-fls`; with `-delete`, both the starting points and the file it writes), `rsync --delete` or output redirect goes through when everything it changes is strictly under one of these, after symlinks are resolved:

- `/tmp`, `/private/tmp`, `/var/tmp`, `/var/folders`, `/private/var/folders` and `$TMPDIR`;
- the session's working directory, when it is a project: not `/`, the home directory or a parent of it, another person's home, a hidden directory in the home directory (`~/.ssh`, `~/.config`) or a system directory (`/etc`, `/usr`, `/var`, `/opt` and the like);
- `~/ag-work`, `~/wt`, `~/tmp` and `~/scratch`;
- Claude Code's worktrees, `…/.claude/worktrees/<name>`.

A root itself never counts (`rm -rf ~/ag-work`, `rm -rf /tmp`), nor does anything in a `.git` directory, whatever its letter case (`.GIT` is `.git` on macOS). A glob is read only in the last name and never as `.` or `..` (`rm -rf /tmp/x/*` goes through; `/tmp/*/x`, `/tmp/.*` and `/tmp/*/` ask). A target behind a symlink is read where the link leads, and a `..` after a link goes to the parent of where it leads, as the kernel reads it (`/tmp/link/../x` is next to the link's target, not `/tmp/x`). A path through a link that leads nowhere yet asks, since the command may make where it leads first. A command that makes links or mounts (`ln`, `mount`) asks.

The check reads the variables the same command sets, so `S=/tmp/v1; for v in e1 e2; do rm -rf $S/$v; done` goes through. It errs toward asking. A variable counts only when every place the command sets it is a plain assignment or a `for … in` list at the top level, between `;` or newlines (not after `&&`, in an `if`, a loop body, a function or a pipeline), with a value that has no quote, space, glob or expansion. It does not count when the name appears anywhere else (`read S`, `export S`, `S+=x`, `printf -v S`), when the command has a command substitution, runs a shell or changes `IFS`, or when it is used before it is set. `$HOME`, `~` and `$TMPDIR` are the hook's own unless the command sets them. A relative target is read against the session's working directory and every directory the command `cd`s to, and counts only when it is scratch against each; a `cd` it cannot read (`cd`, `cd -`, `cd $UNSET`) leaves relative targets with you. A `cd` run through `builtin`, `command`, `time` or zsh's `noglob`, `nocorrect` and `-` counts like a plain one, and so does zsh's `chdir`; after an `eval`, which may `cd` anywhere, relative targets ask. If `CDPATH` is inherited or changed by the command (in zsh also through its tied `cdpath` array), a bare relative `cd` may search outside the working directory, so subsequent relative destructive targets ask too; absolute directories and explicit `./` or `../` operands keep their usual checks. A program run through `xargs`, `find -exec`, `ssh`, `eval`, `env -C`, `sudo -D`/`--chdir`, `sudo -R`/`--chroot`, `sudo -i`/`--login` (whose login shell starts in the target user's home) or a container asks; plain wrappers such as `sudo`, `nice`, `timeout` and `do` do not change anything. A command a sourced script changes behind the hook's back (a `readonly` variable, an alias) is not seen.

The audit entry says why: `scratch: rm` for a deletion in these directories, `setting: deletion: rm` for one the setting let through.

## Persona's own approval card

In a session that Persona started, Persona's hook also receives each `PermissionRequest` and puts a card on your phone. Claude Code does not stop that hook when another hook allows the call, so the card would stay up and the agent would be shown as waiting for you even though the command already ran. After each allow, this hook therefore tells Persona's node on that computer through its socket (`~/.persona/node.sock`, kind `hook.decided`, with the same request input). A node that knows `hook.decided` (nwverse/persona#2648) then shows no card, or withdraws the card it already showed. On an older node, the card stays until it is answered or times out; the command runs either way.

## Persona assistant channel profiles

Persona's assistant normally selects `<persona home>/profiles/<launcher>` as its Claude configuration directory. The extension discovers that `profiles` directory from its own node data directory (`<persona home>/node-plugins/<storage-id>/data`), including when `PERSONA_HOME` is not the default `~/.persona`. Every existing channel's real child directory receives the same tagged settings entry as `~/.claude`; explicit `config_dirs` entries still work and are deduplicated. Discovery does not create a channel, include plain files, follow a final-component directory symlink outside `profiles`, or edit through a profile's `settings.json` symlink. The latter is reported as an error for that automatic profile; an explicitly configured directory keeps the existing symlink-following behavior.

Discovery runs when the node program starts and on each one-minute heartbeat. A new or recreated channel is therefore picked up without a `config_dirs` edit, a removed channel drops out of the status list, and an upgrade replaces every discovered entry with the new executable's command. Disable, uninstall and ordinary shutdown remove only the extension-owned entries, including one Persona seeded in a profile after the last heartbeat. Claude reads settings hooks only at startup: an already-running conversation picks up a newly installed or upgraded hook after its process restarts. A Persona version with first-start profile seeding (nwverse/persona#7636) also covers a brand-new profile's first process; older nodes wait for the next reconciliation and a process restart.

This changes installation coverage only. The eligible tools, permission modes, destructive-command guards, user rules, heartbeat expiry and Persona's own user-identity Lark write confirmation are unchanged.

## Persona assistant writes

Persona's main and supervisor conversations do not run in `bypassPermissions`, so each `Write` or `Edit` of the assistant's own files (charters, plans, notes) puts a card in front of you. Persona's "Always allow in this session" lasts one conversation only. The `assistant_writes` setting (off by default) lets the hook answer those calls too, independently of the bypass rules above. With it on, the hook allows a call only if all of these hold:

- The tool is `Write` or `Edit`, and the mode is not `plan`. `MultiEdit`, `NotebookEdit`, Bash (which includes deletion), MCP tools and network writes are not touched by this setting.
- The call comes from a Persona assistant conversation. For Claude Code, both signals must be present: the hook's environment has `PERSONA_ASSISTANT=1` (or the old name `JARVIS_ASSISTANT=1`), which Persona's node sets only on the Claude Code processes it starts for the assistant, and the conversation's `transcript_path` is in the project of the assistant's directory (`…-persona-assistant…` or `…-jarvis-assistant…`). Claude Code names that project after the directory the process started in; a later `cd` does not change it. For `agy`, Persona's ACP companion runs conversations inside a shared `agy acp` process with transcripts under `<agy dir>/brain/<id>/`, so the session's workspace directories (`workspacePaths` / `cwd`) must resolve to `~/.persona/assistant` or `~/.jarvis/assistant` (or a manager's `assistant-m-<hex>`), with no other project workspace attached. ACP [`additionalDirectories`](https://agentclientprotocol.com/protocol/v1/session-setup) can add session-scoped data roots without changing the primary workspace: version 0.2.34 ignores only `<agy dir>/persona-supervision/<conversation id>` or `<agy dir>/antigravity-cli/persona-supervision/<conversation id>` when that path belongs to the current conversation, and an exact `~/.persona/runtime-packages/persona-antigravity-runtime/<64 lowercase hex>` or `~/.jarvis/runtime-packages/persona-antigravity-runtime/<64 lowercase hex>` directory after symlinks and `..` are resolved. A runtime package directory is only an extra-workspace exemption: it does not qualify as the required assistant workspace or become a writable directory. An unrelated project, a directory outside `<agy dir>`, another data path inside it, another conversation's supervision root, an ordinary agent in another project, or Persona's health space (`…-persona-health`) is never treated as the assistant. Guest conversations (`PERSONA_GUEST` set) never count.
- The file's absolute path, with symlinks and `..` resolved, is strictly inside one of the `assistant_write_dirs` (defaults `~/.jarvis/assistant` and `~/.persona/assistant`, also resolved), and not under that directory's `.claude`, `.gemini`, `.agents`, `.agent`, `_agents`, `_agent` or `.git`, and not its `.mcp.json`, `hooks.json` or `mcp_config.json`. Those would let a conversation change its own settings, skills, hooks or MCP servers.
- The extension's program is running, and no `ask` or `deny` rule of yours could be about the call. A rule for `Edit` counts for `Write` too, as Claude Code applies it.

The settings entry's matcher gets `|Write|Edit` only while the setting is on. Turned off, the entry is the one from before and the hook does not run for those tools. Persona assistant channel profiles receive the entry automatically as described above; a launcher's own configuration directory outside those profiles can still be added to `config_dirs`. Each allow is logged like the others, with the note "Persona assistant conversation, in <directory>".

List only directories you would let the assistant overwrite: the hook trusts the list as given, so `~` or `~/.ssh` would be allowed too. Entries are directories, not patterns; a manager's own assistant directory (`~/.persona/assistant-m-<hex>`) must be listed by its full name. The path is checked when the hook runs and Claude Code writes afterwards, so a symlink swapped in between by another process could redirect the write; changing links needs a Bash call, which this setting does not allow.

## Settings and switches

| Setting | Meaning |
| --- | --- |
| `machines` | The computers where the hook is installed, one switch per macOS or Linux computer. No computer is on after installation; turning one on asks for confirmation first. |
| `allow_destructive` | 删除和覆盖也自动允许 (Auto-allow deleting and overwriting too). Off by default. When on, other Bash deletions and overwrites go through; known root/home deletion targets, dynamic executables, evaluated zsh expansions, forced pushes, permission changes, disk formatting and your own ask and deny rules still ask. The program writes it to `options.json` in its data directory when it starts; the hub restarts it when the setting changes. |
| `assistant_writes` | Persona 助手对话的文件写入也自动允许 (Auto-allow file writes from Persona assistant conversations). Off by default. See [Persona assistant writes](#persona-assistant-writes). |
| `assistant_write_dirs` | The directories those writes may land in, including subdirectories. Defaults to `~/.jarvis/assistant` and `~/.persona/assistant`; a configured list replaces the defaults. |
| `config_dirs` | Additional Claude Code config directories that receive the hook. Defaults to `~/.claude`; `~` is that computer's home directory. Persona assistant channel profiles are discovered automatically and need no entry. Add other directories you use with `CLAUDE_CONFIG_DIR`. A missing directory is skipped and shown on the extension page. |
| `agy_dirs` | Antigravity CLI (`agy`) config directories whose `config/hooks.json` receives the `PreToolUse` hook. Defaults to `~/.gemini`; when left at the default and `~/.gemini` is absent on that computer, it is skipped silently. Add each custom directory you pass to `agy --gemini-dir`. |

The extension does nothing until a computer is switched on. You can turn it off for one computer with its switch, or for every computer by disabling the extension. In either case, the program removes its entry as it stops. Uninstalling or upgrading does the same.

## The settings entry

For Claude Code, the program adds one group to `hooks.PermissionRequest` in `<config dir>/settings.json`. For Antigravity CLI (`agy`), when `<gemini dir>` exists, it writes `<gemini dir>/config/hooks.json` with a `PreToolUse` command hook under `agent-bypass-allow` (answering `{"decision":"auto_approve"}` when allowed so `agy acp` does not raise `session/request_permission`, and printing nothing otherwise so `agy` and Persona ask as usual). For an explicit Claude Code directory or an Antigravity hooks file, a symlink is followed to its target; an automatically discovered assistant profile's settings symlink is rejected as described above:

```json
{"matcher": "Bash|Read|Glob|Grep|LS|NotebookRead|Agent|Task", "hooks": [{"type": "command", "timeout": 10,
  "command": "'<package>/bin/agent-bypass-allow-<platform>' hook --config-dir '<config dir>' --data '<data dir>' --persona-extension=claude-bypass-allow"}]}
```

For agy, [`PreToolUse` and `PostToolUse`](https://www.antigravity.google/docs/hooks) use matcher groups containing a `hooks` handler list. Non-tool events such as `PreInvocation` and `Stop` instead contain flat command handlers; that intentional difference is preserved when the extension edits a shared file. With `assistant_writes` on, the installed entry has this shape:

```json
{
  "sample-hook": {
    "PreToolUse": [
      {
        "matcher": "run_command|read_file|view_file|find_by_name|grep_search|list_dir|invoke_subagent|write_file|write_to_file|edit_file|replace_file_content",
        "hooks": [
          {
            "type": "command",
            "timeout": 10,
            "command": "'<package>/bin/sample-hook-<platform>' hook --gemini-dir '<gemini dir>' --data '<data dir>' --persona-extension=sample-owner"
          }
        ]
      }
    ]
  }
}
```

The agy hook accepts the documented camelCase `toolCall` payload with no `hookEventName`, including `TargetFile` for `write_to_file` and `replace_file_content`, and answers `{"decision":"auto_approve"}` only after the same policy checks.

The trailing `--persona-extension=claude-bypass-allow` tag is a stable hook-ownership marker, not the extension's public identity. Version 0.2.24 keeps generating it so the old 0.2.23 binary can replace or remove the hook after rollback; both old and new marker suffixes are recognized. A mixed group is reduced to one owned hook without touching another tool's entries. Other keys and other tools' hooks keep their order and values, and the file keeps its indent. Before each change, it copies the previous file to `settings.json.claude-bypass-allow.bak`. A file that is not a JSON object is left alone and reported as an error. A session that was already running when you turned a computer on may not pick up the hook until it restarts.

## Audit log

Each auto-allow appends one JSON line to `audit.jsonl` in the program's data directory on that computer (`~/.persona/node-plugins/<storage-id>/data/`, mode 0600; upgraded installations keep `claude-bypass-allow`, fresh installations use `agent-bypass-allow`). The log keeps about the newest 1 MB across two files. Each entry records the time, session id, subagent id (when present), working directory, config directory, the tool, the call's full length, and the call itself: the command for Bash, otherwise the tool's name and what it is about (a path, a pattern, a subagent's type and description). Before the command is stored, it is put on one line, cut to 240 characters, and has likely secrets replaced with `***`: `NAME=value` where the name suggests a token, password or key; `Bearer`/`token` values; `--password`/`--token` flags; `-p` passwords for `mysql` and `sshpass`; the password in `curl -u user:password`; credentials in URLs; and opaque strings of 32 or more characters. This masking is a heuristic, so treat the log as sensitive.

The extension's page in **Settings → Extensions** lists, for each switched-on computer, whether the hook is installed in each config directory and the 30 newest auto-allows.

## Permissions

- **Runs a program on the hub**: only to draw the extension page. It reaches the computers through `nodes.call`, has no network access and holds no hub token.
- **Runs a program on the computers you choose** (`node`), with `files` access. It edits Claude Code's `settings.json` outside its own data directory. It needs no network access and no secrets.

## Upgrading from the former ID

Version 0.2.24 changes the public ID from `claude-bypass-allow` to `agent-bypass-allow`. Its source declares the former ID as `replaces`; the signed market entry carries that declaration, not the runtime manifest. Once the new package and catalog are published, use the same registered market's normal preview and update flow on a hub and nodes that support identity transitions. The confirmation names both IDs. Do not uninstall the former extension or install a local new-ID archive to simulate this upgrade.

The installed record keeps its storage slot, configuration, grants, enabled state, computer switches, contribution choices, auto-update choice and audit data. This extension declares no secrets: the secret list is empty before and after. Its allow rules do not change, and `allow_destructive` remains off by default. Old owner-facing IDs remain compatible with the committed installation, without granting old program tokens a new identity. Rollback restores 0.2.23 and its old ID in the same slot.

The host stops and waits for the old node process, including hook cleanup and heartbeat shutdown, before starting the replacement. The persistent ownership tag and backup suffix above intentionally retain the old spelling; do not manually rewrite them. An incompatible node blocks the transition rather than treating the old ID's disappearance as an uninstall.

## Install

Use the [public market](../installation.md), or package locally from the repository root:

```sh
scripts/package.sh agent-bypass-allow
go -C extensions/agent-bypass-allow test ./...
```

The tests cover the hook's decisions for each tool, the commands that stay with a person, deletions in scratch directories and the variables they use, the `allow_destructive` setting, rule matching, redaction, the audit log, editing settings.json without changing anything else, the program's install and cleanup, and the page in three languages.
